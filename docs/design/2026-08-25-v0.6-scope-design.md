# para-vault-mcp v0.6 — Scope Design

**Date:** 2026-08-25
**Status:** Draft
**Predecessor:** v0.5.0 (shipped 2026-08-01; lab note *Stale state can't hide* published 2026-08-04, companion *The pointer we turned into a log* published 2026-08-16 — v0.5 arc closed end to end)

## Identity

**v0.6 is the release where absence is a signal.**

v0.4 made the row honest: a swallowed parse error stopped masquerading as a confident `[]` and surfaced in a new `dateErrors` field. v0.5 made the content fresh: a pointer to a file became the file's live bytes, so a stale in-context copy could no longer stand in for on-disk truth. Both disciplines assume the same thing — that the record reaches the caller in the first place.

v0.6 closes that assumption. A project whose `_project.md` frontmatter fails to parse is excluded from **every** frontmatter-derived filter in `find_project` — `status`, `area`, `#tag`, `stale_days`, and `updated_since`. It survives only an unfiltered call or a plain-text name query. The file most likely to be mangled by concurrent edits is precisely the one that cannot raise its hand, and there is no channel anywhere in the tool surface that lets a caller ask "which projects failed to parse?"

Receipt (2026-08-14): a real corruption in a work project's `_project.md` — a duplicated `next-action:` span appended after the closing quote, the shape concurrent edits actually produce — went undetected by a `status: active` sweep two days before that project's `due:` date. The daily-review path identified the `stale_days` half; source verification surfaced the `status` / `area` / `#tag` half.

The second theme member is the same disease at a different tool. `daily_review_status` reads today's daily note through a single `readFile(...).catch(() => undefined)`, which conflates "file does not exist" with "file exists but could not be read." A present-but-unreadable note reports as missing — a record removing itself from the view.

The riders (#41, #43, #44, #46) ship in the release under **Changed** / **Fixed** but do not claim the theme. Test-architecture and SDK-deprecation hygiene are adjacent at best, and letting them claim the label would dilute what the theme selects for.

## In Scope

### Anchor feature: `find_project` response envelope (#47)

`find_project` currently returns a bare JSON array (`src/tools/find-project.ts:76`). v0.6 wraps it:

```jsonc
{
  "projects": [ /* ProjectSummary[] — filtered, sorted, limited; per-row shape unchanged */ ],
  "parseFailures": [
    { "name": "PC", "path": "…/1-Projects/PC", "error": "bad indentation of a mapping entry (11:3)" },
    { "name": "Warrior Invictus POC", "path": "…/1-Projects/Warrior Invictus POC",
      "dateErrors": [{ "field": "updated", "value": "2026-13-45" }] }
  ]
}
```

**Contract.**

- `parseFailures` is built from the **filesystem-derived** `name` / `path` channel — `globby("*", { onlyDirectories: true })` at `src/vault/projects.ts:58`. That is the only channel that survives a frontmatter parse failure, which is why `name`-query is currently the sole path by which a corrupted project can be reached.
- Populated **regardless of active filters**. `status`, `area`, `#tag`, `stale_days`, and `updated_since` have no effect on its contents.
- **Excluded from `limit` and `sort`.** `limit` is applied after filtering (`src/vault/projects.ts:81`); if failures were appended into the results array instead, a `limit: 5` call could return five corrupted projects and zero healthy ones, starving the actual query with its own diagnostic.
- **Always present**, `[]` when the vault is clean. A top-level diagnostic channel that vanishes when empty is indistinguishable from a server too old to have one. (This deliberately differs from the per-row `dateErrors`, which stays omitted-when-empty — a row-level field is read in the context of its row; an envelope field is read in the context of the whole response.)
- **Unconditional census, not a delta.** Membership does not depend on which filters were active. A project with a parse problem appears in `parseFailures` on every call, including unfiltered calls where it *also* appears in `projects`. The duplication is intentional: a filter-dependent diagnostic would let a clean-looking response hide a corruption that a different filter would have revealed.
- **One channel covers both failure kinds.** Whole-file YAML failures (`frontmatterError`) and per-field date failures (`dateErrors`) both appear. Rationale: #47's headline harm is *"a corrupted project can never be flagged stale"*, and a well-formed YAML file with `updated: 2026-13-45` produces exactly that harm — it parses fine but is dropped by `stale_days` and `updated_since`. The rule is uniform: **if a parse problem can remove you from a view, you appear here.**

**Breaking.** The top level changes from an array to an object. Ships as a Breaking entry under `### Changed`, following the v0.4 precedent (`lastReviewed` → `last_reviewed`, shipped Breaking in a minor on the pre-1.0 posture).

**Internal API ripple.** The diagnostic must be produced where the filtering happens — inside `findProjects` (`src/vault/projects.ts:69-78`), the only place that still holds the dropped rows. `findProjects` therefore changes return type from `ProjectSummary[]` to `{ projects: ProjectSummary[]; parseFailures: ParseFailure[] }`, which ripples to:

- `src/tools/next-action.ts:27` — calls `findProjects` unfiltered; destructures `.projects`.
- `test/vault/projects.test.ts` — roughly 30 mechanical call sites.

That ripple is the shape of the bug. The fix touches this much precisely because the error channel (`loadProject`, `src/vault/projects.ts:142-160`) and the filter (`findProjects`, :69-78) live at different layers — which is why the error got lost in the first place.

### Theme member: unreadable is not missing (#42)

`inboxStatus` (`src/vault/daily.ts:266`) reads today's note once, and that single `readFile(file, "utf8").catch(() => undefined)` serves triple duty: existence flag, `endOfDayChecks` source, and body source. Every failure mode collapses into "missing."

v0.6 discriminates on `err.code === "ENOENT"` within that same read — no additional I/O:

| Read outcome | `dailyNoteExists` | `endOfDayChecks` | `dailyNoteBody` (when `include_body: true`) | `dailyNoteError` |
| --- | --- | --- | --- | --- |
| `ENOENT` | `false` | `undefined` | omitted | absent |
| Other read error | `true` | `undefined` | `{content: "", truncated: false, totalBytes: 0, error}` | the error message |
| Success | `true` | parsed | envelope | absent |

**New response field:** `dailyNoteError?: string`, present only when the read failed for a reason other than absence. Additive; no existing field is renamed or removed.

**This goes further than issue #42 proposes.** The issue's fix routes only the *opted-in* body path through `readBodyBounded`, deliberately preserving `dailyNoteExists: false` for unreadable files when `include_body` is unset — v0.5's Plan-Level Decision #3 kept the swallow for backward compatibility. v0.6 rejects that boundary: "a present file reports as missing" is the disease the release is named after, and half-fixing it would make the honest answer available only to callers who happened to opt into an unrelated feature. Ships as **Fixed**.

### Rider: exact-`maxBytes` truncation flag (#41)

`buildBodyEnvelope` uses `totalBytes < maxBytes` (`src/vault/daily.ts:21`); `readBodyBounded`'s fast path uses `size <= maxBytes` (:58). A 128 KB-exact daily note would report `truncated: true` for today's note and `truncated: false` for the previous one.

**Resolution: align on strict `<`.** Change `readBodyBounded`'s fast path to `size < maxBytes`. Leave `buildBodyEnvelope` unchanged.

The issue offers "flip both to `<=`" as an equally valid alternative. **It is not — it would introduce a UTF-8 bug.** `readBodyBounded`'s oversized branch (`src/vault/daily.ts:78`) calls `buildBodyEnvelope(buf.toString("utf8"), maxBytes)` with a buffer that is *exactly* `maxBytes`. Under strict `<`, that input falls into the truncation branch and receives the code-point backoff. Under `<=`, it would be returned as-is, with a possibly-split multi-byte character at the tail. The strict comparison is load-bearing for the very safety property the adjacent tests assert.

**Correction to record.** The existing test's rationale comment (`test/vault/daily.test.ts:368-370`) defends `<` on the grounds that a consumer "can't distinguish 'exactly the limit' from 'one byte more, cut at the limit'." That argument does not hold — both paths know the true size (`Buffer.byteLength` in one, `stat` in the other). The convention is correct; the stated reason is not. Update the comment to the real reason: `buildBodyEnvelope`'s truncation branch is what performs the UTF-8 boundary backoff, and the exact-fit input must reach it.

### Rider: SDK-level integration test (#43)

`test/server.test.ts` exercises `buildServer`'s own `listToolNames()` / `callTool()` dispatch map, not the SDK's real `tools/call` path through `registerTool`. Add a test that boots `McpServer` in-process, dispatches a real `tools/list` plus `tools/call` over an in-memory transport, and asserts the response for at least one representative tool.

**Sequenced before the `find_project` envelope change**, so the test is written against the current response shape and witnesses the break, rather than being authored against the new shape and proving nothing.

### Rider: `registerTool` deprecated overload (#44)

`src/server.ts:24-28` passes a raw `ZodRawShape` as `inputSchema`; that overload is deprecated in `@modelcontextprotocol/server@2.0.0`. Wrap with `z.object(...)`. Mechanical, equivalent semantics, no changes needed in `src/tools/*.ts`.

### Rider: CHANGELOG subsection ordering (#46)

Reorder to the Keep a Changelog 1.1.0 canonical sequence — Added → Changed → Deprecated → Removed → Fixed → Security — auditing **every** release section, not only `[0.5.0]`.

## Out of Scope (with reasoning)

- **#45 — `readBodyBounded` UTF-8 double round-trip.** Bounded cost, capped at one extra encode/decode of 128 KB per call. Worth noting it becomes *more* attractive after v0.6: doing the boundary backoff directly on the `Buffer` would decouple `readBodyBounded` from `buildBodyEnvelope`'s strict-`<` behavior, removing the coupling #41 is about to document. Stays unmilestoned.
- **#39 — size-aware response patterns.** Still an unconfirmed receipt; the specific client alert has not been captured. It needs a spike before it can carry scope, and its natural home is a future "size-aware by construction" release, not a diagnostics one.
- **#6 — MCP directory submissions.** Its own pre-submission checklist still has "at least one external user has confirmed install works against their vault" and "issue-triage cadence established" unchecked.
- **#7 — `get_captures_today`.** A new tool surface would dilute a release whose entire claim is about the honesty of existing surfaces.
- **Project-index health count on `daily_review_status`** (suggested in #47's proposed-fix sketch). `daily_review_status` is the only tool that touches nothing but the daily note and the inbox, and #7 defends that narrowness explicitly as a design property. Adding a project scan would make the review opener walk `1-Projects/` on every call and would maintain a second copy of a signal that the envelope fix already places on the tool that answers project questions. Revisit only if a receipt shows a review path that never calls `find_project`.
- **`next_action` response envelope.** `next_action` also returns a bare array, but a project with unparseable frontmatter is *not* dropped from it — the tool calls `findProjects` unfiltered, and `getNextAction` falls back to the first unchecked task regardless of frontmatter validity. No record removes itself from that view, so the theme does not select it. `next_action` changes only by destructuring the new return type.

### Testing

TDD throughout. `test/helpers/tmp-vault.ts` copies the shared fixture into a temp directory, so corrupted projects are created in temp vaults and `test/fixtures/vault/` stays clean — no ripple into existing name and count assertions.

New coverage:

- **`parseFailures` census.** A corrupt project appears in `parseFailures` under each of `status`, `area`, `#tag`, `stale_days`, `updated_since`, and under `limit: 1`. This is the reproduction table from issue #47 turned into assertions.
- **`parseFailures` is `[]`, not absent,** against a clean vault.
- **Date-error rows** appear in `parseFailures` per the one-channel rule.
- **Unconditional census.** A corrupt project appears in *both* `projects` and `parseFailures` on an unfiltered call.
- **`next_action`** still resolves against the new `findProjects` return type.
- **#42 read-error path.** The forced error must be non-`ENOENT` and reliable on every CI leg. **Do not use `chmod 000`** — it is a no-op for root, which is what CI containers commonly run as, so the test would silently pass by successfully reading the file. **Point the daily-note path at a directory instead:** `readFile` on a directory yields `EISDIR` on both Linux and macOS with no privilege dependency.
- **#41** exact-`maxBytes` parity between `buildBodyEnvelope` and `readBodyBounded`, plus a regression test that the exact-fit path still performs the UTF-8 backoff.
- **#43** in-process `tools/list` and `tools/call` round trip.

## Resolved Decisions

1. **Envelope, not append-to-results or opt-in filter.** Appending failures into the results array keeps the response non-breaking but breaks the "everything here matched your filter" contract and lets `limit` be consumed by diagnostics. An opt-in `has_errors: true` filter is cheapest but requires the caller to know to ask — which is the current failure mode restated, as #47's own analysis notes.
2. **`parseFailures` always present, `[]` when clean.** Absence of the key would be indistinguishable from an older server.
3. **One channel for both `frontmatterError` and `dateErrors`.** Uniform rule: if a parse problem can remove you from a view, you appear here.
4. **Unconditional census, not a delta.** Membership is filter-independent; duplication with `projects` on unfiltered calls is intentional.
5. **No project-health count on `daily_review_status`.** See Out of Scope.
6. **#42 fixed fully, not in the conservative opt-in-only form the issue proposes.** See the theme-member section.
7. **#41 aligns on strict `<`, not `<=`.** `<=` would break UTF-8 boundary safety in `readBodyBounded`'s oversized branch. The existing test's rationale comment states a reason that does not hold and is corrected as part of the change.
8. **Riders are #41, #43, #44, #46.** #45 and #39 stay in the backlog, unmilestoned.
9. **#43 sequenced before #47**, so the integration test is authored against the pre-break response shape.

## Deferred to Implementation Plan

- Exact `ParseFailure` field names and the shape used when a single project carries *both* a `frontmatterError` and `dateErrors`.
- Whether `ParseFailure.path` is absolute (matching `ProjectSummary.path`) or vault-relative.
- The in-memory transport mechanism for #43, pending the SDK v2 API surface.
- Whether the `_`-prefixed key filter in `find_project`'s `JSON.stringify` replacer (`src/tools/find-project.ts:76`) needs adjustment for the new envelope nesting.

## Risks Accepted

- **Breaking response shape.** Any consumer parsing `find_project`'s top level as an array breaks. Mitigated by the pre-1.0 posture, an explicit CHANGELOG Breaking entry, and the v0.4 precedent. Blast radius is plausibly the maintainer alone — #6 (directory listings) has never shipped, so there is no known external install base.
- **`dailyNoteExists` semantics change without opt-in.** A present-but-unreadable note now reports `true` instead of `false`. This is a strictly more honest answer, but it is a behavior change for callers that never asked for one. Documented under Fixed.
- **Two release surfaces changing at once.** Both `find_project` and `daily_review_status` change response shape in the same release. The waves keep them in separate files, and #43's integration test provides a floor under the SDK-facing registration path.
