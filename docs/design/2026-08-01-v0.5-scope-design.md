# para-vault-mcp v0.5 — Scope Design

**Date:** 2026-08-01
**Status:** Draft
**Predecessor:** v0.4.0 (shipped 2026-06-26, lab note published 2026-07-03 — *Make the silence loud*)

## Identity

**v0.5 is the release where freshness is structural.**

v0.4 made silences loud — the tool refused to hand back a confident-looking answer that had actually swallowed an error. v0.5 extends that discipline to a subtler class of wrong answers: **stale ones.** Not swallowed errors — *stale references.* A pointer to a file is a stand-in for the file's contents; a summary field is a stand-in for the state it summarizes. Both can quietly diverge from what they point at, and both did during 2026-07 dogfooding.

Receipt #1 (2026-07-08): a daily review ran off a stale in-context copy of the daily note and missed live edits — a meeting log, a substantial PC investigation, inline watch-item resolutions. Root cause: `daily_review_status` — the tool called at the *start* of every review — returns **pointers** (`today's path`, `previousDailyNotePath`), and that indirection is exactly what let the fresh on-disk read get skipped. Receipt #2 (2026-07-23): a project's `next-action` frontmatter drifted from an executable pointer into a ~5,600-char running status-log while the `## Log` already had three later entries. Same insight from the content side: a summary field diverges from reality because keeping it current is expensive, so it lags.

v0.5 collapses the reference-to-reality gap at the tool boundary that owns receipt #1. The daily-review opener stops handing out pointers alone; on request, it hands out the live on-disk body of today's daily note (and optionally the previous note's), so the "reviewer read a stale in-context copy" failure mode becomes structurally impossible instead of a caller-side discipline. Receipt #2 produced a vault convention (`_system/PARA-conventions.md` → "The `next-action` field") but no v0.5 tool change — see Out of Scope.

Modernization work (pnpm 11 bump, Node baseline bump, SDK v2 investigation) rides in the release under **Changed** but does not claim theme membership. The tight version of "reference diverging from reality" is what earns the label; version-currency is a thematic cousin at best, and letting it claim the label would dilute what the theme actually selects for.

## In Scope

### Anchor feature: `daily_review_status.include_body`

The single new feature in v0.5. Two optional boolean params on `daily_review_status`; two optional response fields carrying the live on-disk bodies with explicit truncation reporting.

**New input params** (both default `false`):
```ts
include_body?: boolean          // include today's daily-note body
include_previous_body?: boolean // include the previous daily note's body
```

**New response fields** (present only when the corresponding param is `true` and the file exists):
```ts
dailyNoteBody?:         { content: string; truncated: boolean; totalBytes: number }
previousDailyNoteBody?: { content: string; truncated: boolean; totalBytes: number }
```

**Truncation.** Hard byte limit of **128 KB**, constant, unconfigurable in v0.5. If the on-disk file exceeds the limit, `content` is the first 128 KB read as UTF-8 (with the byte-boundary cut backed off to the last complete code point), `truncated: true`, `totalBytes` is the full file size in bytes. Anything under the limit: `truncated: false`, `totalBytes === Buffer.byteLength(content, 'utf8')`.

**Freshness invariant.** The body is read at tool-call time. No caching in the tool. That is the entire point — the receipt's failure mode was the caller trusting a *not*-freshly-read copy, and if the tool itself caches then we've reproduced the bug at a different layer.

**Absence behavior.** If today's daily note doesn't exist, `dailyNoteBody` is omitted from the response (the existing `dailyNoteExists: false` already communicates the state). Same for `previousDailyNoteBody` when there is no prior daily note. The `include_body` param being `true` does not *create* a missing daily note — this tool is a status report, not an editor.

**Empty-file behavior.** A daily note that exists but is empty (0 bytes) returns the envelope populated: `{content: "", truncated: false, totalBytes: 0}`. The distinction matters — "file present but empty" is a legitimate state (the reviewer created the note but hasn't written anything yet), and omitting the field would collapse it into "missing" incorrectly.

**Backward compatibility.** Existing callers see identical responses (both params default `false`; new fields absent). No response field renamed or removed.

### Modernization rider: pnpm 11

Dev-only bump. Zero user impact — `packageManager` field only, no runtime change.

- `packageManager: pnpm@10.33.0` → `pnpm@11.18.0` in `package.json`.
- Regenerate `pnpm-lock.yaml`.
- Verify `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm test` pass locally and across the (v0.5-bumped) CI Node matrix.

Rationale: pnpm 11 is the current stable line (`next-11: 11.19.0` — patches still landing) and pnpm 12 is at `12.0.0-beta.3`, too early to wait for. Waiting for 12 would mean shipping v0.5 on a soon-to-be-superseded major.

### Modernization rider: Node baseline (drop 20, add 26)

Breaking change to `engines.node` and CI matrix. Blast radius is small for a library the user installs via `npx` and picks their own Node for, but *is* user-visible and belongs in the CHANGELOG's `Changed` block with a **Breaking** marker.

- `package.json` `engines.node`: `>=20` → `>=22`.
- `.github/workflows/ci.yml` matrix: `[20, 22, 24]` → `[22, 24, 26]`.
- `.github/workflows/release.yml` publish job: `node-version: 20` → `node-version: 22` (long-tail LTS for the publish path).

Rationale: Node 20 is out of active LTS; keeping it in CI is dead weight, and 26 is now a real target. Aligns published minimums with current-reality rather than legacy-reality.

### Modernization investigation: MCP SDK v2

Not a feature; a **decision-gated investigation** whose output determines whether SDK v2 rides v0.5 or defers to v0.6.

**Scope of the investigation:**
1. On a disposable scratch branch off `feat/v0.5`, install `@modelcontextprotocol/codemod` and run it against `src/`.
2. Capture the codemod output — the diff, any warnings, any unresolved rewrites — as a scratch artifact.
3. Read the diff. Answer the fold-or-defer question against the criteria below.

**Fold-into-v0.5 criteria (all must hold):**
- Diff touches only `src/index.ts` + `src/server.ts` + the five `src/tools/*.ts` files.
- No tool contracts change (Zod input schemas unchanged; response shapes unchanged).
- Codemod completes with no unresolved rewrites.
- Total LOC delta under ~100.

**Defer-to-v0.6 criteria (any one triggers):**
- Any tool contract requires reshaping (breaking API surface for consumers).
- Codemod leaves unresolved rewrites.
- Transport or error-handling migration is non-mechanical.
- LOC delta over ~200, or diff touches `src/vault/` code.

**Middle zone (100–200 LOC, all mechanical):** judgment call, re-open a small brainstorm rather than deciding on gut. Prefer defer if uncertain — v0.6 has room for a first-class migration release; v0.5's theme should not be crowded out by a plumbing story that under-delivered.

Whichever way it lands, **document the codemod output** as a lab-note observation for the v0.5 write-up. "Here's what codemod-driven MCP SDK migration actually looks like on a small server" is content the AI Practice can use regardless of the fold-or-defer outcome.

## Out of Scope (with reasoning)

- **Drift detection on `next-action` (receipt #2's other half).** Any implementation that meaningfully detects "the frontmatter next-action has drifted from the newest `## Log` entry" requires the tool to know what `## Log` (or `## Activity`, or `## Journal`) means as a section. That is user-specific convention encoding, which violates the [[feedback-tools-vs-conventions|substrate-vs-convention]] rule (issue #7) whether the section name is a literal or a config knob. A convention-agnostic version — flag any `next-action` whose length exceeds a threshold — works as substrate-level hygiene but is thematically weaker: it is "next-action shape enforcement," not "reference diverging from reality." Deferred without milestone; the convention captured on the vault side (`_system/PARA-conventions.md`) is doing the work receipt #2 asked for.
- **Generalized "read tools return bodies" pattern.** Extending the live-body pattern to `next_action` (returning bulleted-list content) and `find_project` (returning `_project.md` bodies) coheres with the theme but has no receipt yet, and — critically — needs a first-class response to the size story before it can ship. Issue #39 captures the receipt-in-waiting and marks this as v0.6+ territory once the size-aware pattern is designed.
- **PR #29 doc-cleanup findings** (README `next_action` body-fallback sentence; "91 tests as of v0.3" refresh). Cleanup fits any release. Not theme. Land opportunistically or in a v0.5.x patch.
- **`@11ty/gray-matter` cache-bug PR (`11ty/gray-matter#9`).** External track. Awaiting the maintainer's A/B call on the fix approach; a reminder-agent is scheduled for 2026-08-08 (`trig_01C95wU2MXM7qmCD5UN6fehN`).

## Sequencing

Single branch, serial (Approach A from brainstorm).

```
Wave 1 — Small modernization deps land first (confidence-builders)
  1a. chore(deps): bump pnpm to 11.18.0
  1b. chore(node): bump baseline to 22, CI matrix [22,24,26], engines >=22
  Both small, both isolated. Green CI after each proves the branch's
  toolchain works before we touch anything semantic.

Wave 2 — SDK v2 investigation (decision gate)
  Run @modelcontextprotocol/codemod on a scratch subtree of the branch.
  Read the diff against the fold/defer criteria. If fold: apply codemod
  as one atomic commit, verify tests + typecheck green. If defer: commit
  the investigation artifact under docs/design/ (or as a comment on a
  new v0.6-anchor issue), leave SDK on ^1.30.0 for v0.5.

Wave 3 — Anchor feature (the release exists for this)
  Implement in natural sub-slices, one commit each per the atomic-commits
  preference:
    a. Zod schema extension (two optional booleans on
       dailyReviewStatusInputSchema).
    b. readBodyBounded helper in src/vault/daily.ts (pure, testable).
    c. inboxStatus signature extension to accept include-body options
       and populate the new response fields via readBodyBounded.
    d. Tests: readBodyBounded unit tests (happy path, exact boundary,
       multi-byte UTF-8 at boundary, missing file, empty file);
       inboxStatus tests for the four param combinations; tool-level
       integration test; freshness-invariant test (write, call, mutate,
       call again, assert content changed).
    e. Tool description + Zod .describe() refresh reflecting the new
       params and truncation contract.

Wave 4 — Release
  CHANGELOG [Unreleased] → [0.5.0] with date, prose-led entries grouped
  under Added / Changed subheadings. Version bump to 0.5.0. Tag, GitHub
  release, npm publish via existing OIDC workflow. Lab-note draft
  post-release, cross-post LI/BS/X.
```

- **Wave 1 lands first.** Both changes are self-contained and unblock nothing themselves, but the CI-matrix bump in particular has to be settled before feature work exercises it — a matrix change that breaks alongside a feature change is harder to bisect than a matrix change that breaks alone.
- **Wave 2 gates before feature work starts.** Implementing the anchor twice — once against SDK 1.30, once against v2 if the codemod succeeds — is the failure mode Approach A exists to prevent. Investigation is cheap (1–2 hours max); waiting the additional gate on it is the right price.
- **Wave 3 sub-slices are atomic per the [[feedback-atomic-commits|atomic-commits preference]].** The Zod schema addition, the pure helper, the wiring, the tests, and the doc refresh are each independently reviewable.
- **`_project.md` gets a same-session log entry** on any material action per the CLAUDE.md rule — at minimum: after Wave 1 lands, after the Wave 2 fold-or-defer decision, and after v0.5.0 tags.

## Done Criteria

v0.5 ships when all of the following are true:

1. **Anchor freshness invariant verified.** A test writes a fixture daily note, calls `daily_review_status({include_body: true})`, mutates the fixture on disk, calls again — assertion: the second call returns the mutated content. Any in-tool caching that would break this assertion is a bug, not an optimization.
2. **Truncation contract verified.** A daily-note fixture just under 128 KB returns `truncated: false, totalBytes === content.byteLength`. A fixture over 128 KB returns `truncated: true, totalBytes === (real file size), content.length === 128 KB (or less due to the multi-byte-safe backoff)`. A fixture with a multi-byte UTF-8 code point straddling the 128 KB boundary returns valid UTF-8 (does not split a code point).
3. **Backward compatibility verified.** Calling `daily_review_status` with no args (or with both new booleans explicitly `false`) returns a response byte-identical to v0.4's response for the same vault state. Existing tests that assert response shape stay green with no edits.
4. **Absence behavior verified.** When today's daily note does not exist, `dailyNoteBody` is *omitted* (not present with `content: ""`). When there is no prior daily note, `previousDailyNoteBody` is omitted. `include_body: true` does not create a missing daily note.
5. **Node baseline effective.** `engines.node` reads `>=22`. CI matrix is `[22, 24, 26]`. Release workflow's publish step targets Node 22. All three matrix legs pass typecheck + tests.
6. **pnpm 11 effective.** `packageManager` reads `pnpm@11.18.0`. `pnpm install --frozen-lockfile` in CI resolves cleanly against the regenerated lockfile.
7. **SDK v2 decision documented.** Either (fold path) the SDK v2 codemod diff is applied and tests remain green, and the CHANGELOG names the migration; or (defer path) the investigation output is committed under `docs/design/` (or referenced from an open v0.6 issue) with the specific criteria that triggered the deferral.
8. **CHANGELOG `[Unreleased]` promoted to `[0.5.0]`** with date, prose-led, grouped under **Added** (anchor), **Changed** (pnpm, Node, SDK if folded), and — if applicable — **Fixed** / **Security**.
9. **npm publish** via the existing OIDC trusted-publishing path. `@robertwtucker/para-vault-mcp@0.5.0` is `latest` on the registry.
10. **No open `v0.5` milestone issues remain.**

## Resolved Decisions

- **The release identity is "freshness by construction," not "modernization + a feature."** Even though the modernization surface (pnpm, Node, potentially SDK v2) is substantial, letting version-currency claim theme membership would dilute what "reference diverging from reality" selects for. Modernization ships under `Changed` and the lab note stays about the anchor.
- **Anchor param shape: two booleans, not one object.** `include_body: {today?, previous?, maxBytes?}` is more powerful but nested; two booleans compose better with agent reasoning and invite less feature creep. If a real receipt for caller-configurable `maxBytes` shows up, add it in v0.6 — issue #39 is the venue.
- **Truncation limit: 128 KB, constant, unconfigurable in v0.5.** The default is calibrated for daily notes (typical 2–8 KB, long meeting-heavy days 20–50 KB) with headroom for weekly-review variants. It intentionally does *not* accommodate large project files — those are `find_project`'s hypothetical future problem, filed as issue #39. 128 KB also aligns with typical LLM-side read tool defaults, reducing the double-truncation surprise.
- **No in-tool caching of body content.** The tool's promise is freshness on read. Any layer that caches — request-scoped, process-scoped, mtime-invalidated — reintroduces the exact failure mode the receipt described. The freshness-invariant test in Done Criteria #1 makes this a first-class contract, not an incidental implementation detail.
- **Absence yields omission, not empty envelope.** A missing daily note produces no `dailyNoteBody` field, not `{content: "", truncated: false, totalBytes: 0}`. The empty envelope is ambiguous (is the file empty, or missing?); the existing `dailyNoteExists: false` already carries the state.
- **Drift detection excluded, not deferred.** The convention-agnostic version (length threshold) is achievable but doesn't earn theme membership. The convention-dependent version (`## Log` awareness) violates the substrate-vs-convention rule. Receipt #2 is served by the vault-side convention doc, not by a tool change.
- **SDK v2 uses a decision-gated investigation, not a scope commitment.** Committing to v2 in the spec before running the codemod would be theatre — we don't have the data. The spec commits to running the investigation and to the criteria that decide the outcome, which is the honest form of the commitment.
- **Modernization work does not defer.** pnpm 11 and the Node baseline bump are small and independent of theme; they ride v0.5 because deferring them would produce a v0.5.x follow-up with no new content, which is a worse consumer experience than one release with one Breaking-marked bullet.

## Deferred to Implementation Plan

- **`readBodyBounded` internal shape.** Whether to use a streaming read with a byte counter, a `readFile` + `Buffer.slice` + `TextDecoder({fatal: false, ignoreBOM: false})` with a trailing-code-point backoff, or an intermediate approach, is a plan-level call. Constraint: multi-byte UTF-8 code point at the boundary must not be split. The plan picks the mechanism.
- **`inboxStatus` signature extension shape.** The existing signature is `inboxStatus(vaultPath, date, config)`. Options can go on a fourth trailing parameter object (`{includeBody?, includePreviousBody?}`), or by re-signaturing to take a single `{vaultPath, date, config, includeBody?, includePreviousBody?}` bag. The trailing options object matches the existing house style (see `capture`'s options handling) and is the presumptive choice; plan confirms.
- **Test-fixture organization.** Whether to add new `daily-note-*.md` fixtures under an existing `test/fixtures/` tree or create a sub-tree specifically for body-return cases is plan-level. Large-file fixtures (for the truncation-boundary tests) may want to be generated at test time rather than committed as literal files.
- **Codemod artifact storage (Wave 2).** Whether the scratch-branch codemod output lives as a committed artifact under `docs/design/2026-08-XX-sdk-v2-investigation.md`, as a comment on a new GH issue, or in the [Unreleased] CHANGELOG entry itself, is plan-level and depends on the fold-or-defer outcome. The spec commits to *documenting* the output; the venue is plan-level.
- **Node 26 CI-runner availability.** GitHub-hosted runners' support for Node 26 as an `actions/setup-node` target may need a `node-version: '26.x'` or a specific patch pin depending on availability at implementation time. Plan resolves at PR-author time.
- **Body-read failure behavior.** The existing `inboxStatus` code path swallows read errors on the daily-note existence check via `readFile(file, "utf8").catch(() => undefined)` — a v0.4-era silence that predates the freshness discipline. For the new body-return path, options are (a) preserve the swallow-and-omit pattern for consistency, (b) surface a per-field error envelope (`dailyNoteBody: {error: "..."}`), or (c) let the read error propagate and fail the whole tool call loudly. Option (c) aligns with v0.4 discipline but disrupts a call that returns useful info even without the body; option (b) adds contract surface for a rare case; option (a) reintroduces a silence at the exact layer this release exists to close. Plan picks; recommend (b) with a small carrier so the caller can distinguish "body unavailable due to error" from "body omitted because file missing."

## Risks Accepted

- **The freshness-invariant test can pass in unit-test isolation while a caching bug lurks at a different layer.** Node's own fs cache, an fs shim in a test harness, or an MCP-transport-level cache could all reintroduce the failure mode the anchor exists to close. Mitigation: the freshness test writes a real file (not a mock) and mutates via the same `fs` module the tool uses. The test asserts *observed content differs across calls*, not just *the tool re-invoked the read function*. If we ever add an fs abstraction layer, the test moves with it.
- **The 128 KB truncation ceiling is a judgment call.** Set too low, it truncates real weekly-review dailies; set too high, it becomes the default response size that clients complain about downstream. 128 KB is calibrated against the maintainer's observed distribution (dailies ≤10 KB, weeklies larger but bounded) and typical LLM-tool boundaries. If real users hit the ceiling on legitimate content, revisit in v0.5.x — the value is a single constant in one file, and issue #39 is already the venue for a caller-configurable follow-up.
- **The multi-byte UTF-8 backoff at the truncation boundary is easy to get slightly wrong.** A naive `TextDecoder` invocation with `{fatal: true}` throws on partial code points; a permissive decoder silently emits U+FFFD replacement characters, which is itself a silence. Mitigation: `readBodyBounded` unit tests explicitly cover the boundary case with a fixture whose code-point boundaries are known; the implementation targets a byte-count backoff to the last complete code point, not a decoder trick.
- **SDK v2's fold-or-defer criteria may not survive contact with the codemod output.** The criteria assume the codemod exists as advertised and produces a diff we can classify. If the codemod is buggy, incomplete, or changes semantics in ways the diff doesn't obviously show, the fold-if criteria become inadequate. Mitigation: defer is always safe; when in doubt, defer. v0.6 has room for a first-class migration release.
- **The Node baseline bump is user-visible for anyone still on Node 20.** Users on 20 will see `npx` fail with an engines mismatch. Mitigation: the CHANGELOG entry names the change with **Breaking**; the v0.5 lab note calls it out; the pre-1.0 semver posture makes this legitimate. Not enough real users to warrant a graceful-degradation path.
- **The lab note's arc — v0.4 defensive → v0.5 offensive — is retrofit.** Neither release was originally planned as part of an arc; the arc is being recognized after the fact. Fine for the essay, risky if it becomes a template ("v0.6 must extend the arc further"). Mitigation: the arc is a lens, not a commitment. v0.6's theme is set by v0.6's receipts, not by narrative continuity.
